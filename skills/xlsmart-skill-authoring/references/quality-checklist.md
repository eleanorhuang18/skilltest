# 交付前自检清单

逐条打勾，任何一条不过就改。不要用"以后补"跳过。

## 定位

- [ ] 一句话能说清它解决什么问题，没有"并且/顺便/也支持"。
- [ ] 和仓库里已有 skill 不重叠；重叠就先合并或明确分工。
- [ ] 业务线归属清晰（套餐售卖 / 客客服 / 运营统计）。

## 描述（description）

- [ ] 前 60 个字符是触发场景，不是功能吹嘘。
- [ ] 含用户真实会说的中文原话，例如"这个套餐为什么卖不动"。
- [ ] 含英文触发词（如果团队有英文使用者）。
- [ ] 没有"强大/全面/智能/一站式"这类形容词。

## 正文

- [ ] 步骤编号，每步有可检查的完成条件。
- [ ] 表名、字段名、指标口径有出处或明确标注"待业务确认"。
- [ ] 有产出格式，且给了最小示例。
- [ ] 写清了不适用场景，避免误触发。
- [ ] 异常路径有交代：数据为空、查询失败、权限不足分别怎么办。
- [ ] 全文 < 10,000 字符；超了就把查表内容挪到 `references/`。

## 数据与安全

- [ ] 只读，不含任何写库语句。
- [ ] 无 token / 密码 / 连接串 / 内网 IP / 员工手机号 / 客户明细。
- [ ] 示例数据是脱敏的，量级真实。
- [ ] 不要求把敏感结果发到外部渠道。

## 可执行性

- [ ] 换一个人（或另一个 agent）照着做，不需要再问你，能走完。
- [ ] 有脚本的：脚本存在的路径、入参、退出码和正文写的一致。
- [ ] 有脚本的：跑过一次最小样例，确实能出结果。

## 仓库

- [ ] 目录名 kebab-case，与 `name` 一致。
- [ ] `README.md` 索引表已加行。
- [ ] commit 信息符合 `feat(skill):` / `fix(skill):` 规范。
- [ ] 推送后回读远端确认 commit 存在。
